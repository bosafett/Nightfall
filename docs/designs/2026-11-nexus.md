# NEXUS: workflow orchestration (design for review)

Status: **design only, 2026-11-07.** Nothing here is built. NEXUS stays a "Planned" label in the sidebar until a
version of this is approved and built.

## 1. What NEXUS is

Addendum 5 §10: a **common workflow engine** that coordinates multi-stage work across SWORD and SHIELD, instead of
orchestration logic living inside individual agents or tools. Its requirements:

- explicit workflow states, defined dependencies;
- execution timeouts, failure handling, retry policies;
- approval checkpoints, cancellation;
- audit logging, evidence association;
- **it must not bypass CONTROL**, and **no workflow inherits broader permissions than its individual approved steps.**

### What exists today

- **BLACK OPS playbooks:** a run writes one ordinary operation per step, all at once. There are no dependencies
  between steps, no waiting on results and no human tasks in between.
- **Operations:** the worker claims them, re-checks scope, approval and profile, and retries a crashed job at most
  3 times.
- **Agents:** the director can plan, but agents only propose. A person decides.
- **CONTROL:** one approval-lifetime rule (lab 24 h, live 72 h), route-level permission checks, fresh two-factor for
  sensitive actions.

What's missing is the step *between* these: "when X finishes, and only if its results say Y, do Z after a person
agrees". NEXUS adds that and nothing else.

### The example workflow from Addendum 5, against what's built

| # | Step | Today |
|---|---|---|
| 1 | SWORD discovers an exposure | Built (operations, playbooks) |
| 2 | BLACK ICE correlates it | Built (finding rules, contradiction flags) |
| 3 | ATLAS associates the asset | Built (assets, status, history) |
| 4 | NEXUS creates a defensive review task | **This design** |
| 5–6 | SHIELD evaluates; AEGIS recommends a countermeasure | Not built (SHIELD waits on the recurring-runs decision) |
| 7–8 | CONTROL evaluates; the operator approves | Built (per operation) |
| 9 | An authorized integration executes the countermeasure | Not built (no integrations; Addendum 5 forbids agents changing infrastructure) |
| 10 | SWORD reassesses | Built (re-running a collector) |
| 11 | BLACK ICE records the evidence | Built |
| 12 | CHRONICLE preserves the timeline | Planned (reads NEXUS runs once both exist) |

So v1 can run steps 1–4, 7–8 and 10–12. Steps 5, 6 and 9 appear in the UI as **unavailable step kinds**. A
workflow that needs one can't be started, and nothing pretends to do them.

## 2. Principles

1. **NEXUS holds no permissions of its own.** It can't approve, can't execute and has no database role. Every step
   that does something goes through the *same function* a person would use (proposing an operation, launching a
   playbook, recording a decision). Those functions run with the person's identity and the same checks.
2. **Checks happen when a step starts, not when the workflow starts.**
   - Permission, scope, the target's registration, proof of control (for Profile B later) and budgets are evaluated
     again for every step at the moment it starts.
   - A role change, a new scope version, a retired ownership claim or an expired approval stops the next step. It
     doesn't carry on under the old decision.
3. **Approving a workflow doesn't approve its steps.**
   - Starting a run is a decision to *begin*. Each step that contacts a target gets its own approval through the
     existing approval flow, at the time it is due.
   - There is no "approve all steps" button.
4. **Definitions are reviewed code**, like playbooks: versioned, fingerprinted, listed with their tests. Nothing comes
   from a user or a model except the project, a target from the active scope, and choices from fixed lists.
5. **AI can suggest, not start.** An agent may recommend a workflow in text. Starting it is a person's action, and
   agent steps inside a workflow produce hypotheses only (as now).
6. **No simulated progress.** A step is shown as done only when the thing it waited for really happened (an operation
   succeeded, a person decided). Unbuilt step kinds show as unavailable.

## 3. Model

### Definitions (in code)

A workflow definition has an id, name, version, summary, the profiles it may run under, its steps, an overall
deadline and its tests. Each step has:

- `key`, `label` and `kind` (below);
- `depends_on`: the keys of steps that must be done first (a DAG, checked at import: no cycles, no unknown keys);
- `when`: an optional condition from a **fixed set of predicates**, never code or expressions from data. Examples:
  "step S produced at least one open finding of severity ≥ high", "a person marked finding(s) remediated", "always";
- `timeout`, plus `retries` (0 by default; see §5);
- kind-specific parameters (e.g. which collector, which playbook).

### Step kinds

| Kind | What it does | Approval |
|---|---|---|
| `playbook` | Launches a BLACK OPS run through its normal preflight and launch path | Per operation, as now |
| `operation` | Proposes one collector operation on a target from the active scope | As now: passive runs without one, low and above need one |
| `review` | A task for a person: "review these findings", "confirm the asset" | It *is* the human decision |
| `checkpoint` | Waits for an explicit "continue" or "stop" from someone with the stated permission (two-factor required) | It is the approval |
| `agent` | Queues an agent task (analyst summary, adversary hypotheses) | Output is AI-labelled, never verified |
| `wait` | Waits for a predicate (e.g. the remediation date has passed and a person marked it fixed) | None: it sends nothing |
| `shield.*`, `integration.*` | **Unavailable in v1** | n/a |

### State machine

**Workflow run:** `running` → one of `succeeded`, `failed`, `cancelled` or `timed_out`.

**Step:**

```
pending ──deps done, when=true──▶ ready ──started──▶ running ──▶ succeeded
   │                                │                   │
   └─ when=false ─▶ skipped         └─ start refused ─▶ blocked (reason shown; a person can retry or cancel)
                                                        ├──▶ failed / timed_out (→ retry, if allowed)
                                                        └──▶ cancelled
```

- `running` for an `operation` or `playbook` step means its operations exist. Success means all of them succeeded.
  A denied or rejected operation fails the step and is never retried automatically.
- A run succeeds when every step has succeeded or been skipped. It fails when a failed step has dependants that can't
  continue.
- Allowed transitions are enforced by a database trigger, as for operations, so no code path can jump states.

### Who advances a run

- **Advancing** means recomputing which steps are ready, evaluating predicates and noticing finished operations. It is
  idempotent, takes a row lock on the run and changes only workflow tables.
- It runs:
  - when a person opens or acts on the run;
  - when an operation's status changes (the API sees this when it reads the operation);
  - on the existing on-demand worker kick.
- No scheduler is added: recurring execution is still an owner decision.
- **Starting a step that sends anything needs a person** in v1. "Ready" steps of kinds `operation` and `playbook`
  show a **Start** button that runs the normal preflight as that person. Owner decision D3 can allow passive steps to
  start automatically on behalf of the person who started the run. Even then they are passive only, and are
  re-checked at that moment.

## 4. Data model (one migration; nothing written yet)

- **`workflow_runs`:**
  - workspace, project, scope version at start (for display only: each step pins its own);
  - definition id, version and fingerprint;
  - started by, state, started at, deadline, finished at, cancelled by and reason.
- **`workflow_steps`:**
  - run, step key, kind, state, attempt, depends_on (copied from the definition);
  - started by (person), started at, deadline, finished at, outcome detail;
  - links: operation ids, playbook run id, agent task id, the decision's audit event id.
- **`workflow_step_events`:** an insert-only row per transition (from, to, by whom, why). This is the history
  CHRONICLE will read, so it isn't rebuilt from the audit log.
- **Row-level security** by workspace on all three tables.
  - The app role may insert runs and steps and update only the `state` and outcome columns, through the transition
    trigger.
  - The worker role may read them.
  - Nobody may delete.
- **Evidence association:** none stored. A step links to its operations, and operations already link to their
  evidence, so the run page and reports follow those links.

## 5. Timeouts, failures, retries, cancellation

- **Timeouts:**
  - Each step has a timeout (default 2 h for `operation` and `playbook` steps, 7 days for `review` and
    `checkpoint`), and the run has an overall deadline.
  - A timed-out step's queued operations are cancelled through the existing cancel path. Running ones finish, and
    their results are kept but don't advance the run.
- **Retries:**
  - Allowed only where the definition says so (at most 2), only for `failed` or `timed_out`, never for `denied` or
    `rejected`.
  - A retry of a step that contacts a target is a **new** operation that needs its own approval if its risk requires
    one. NEXUS never re-uses an approval.
  - The worker's own crash retry (3 attempts) is unchanged and separate.
- **Failure:** the run shows which step failed and why. Steps that don't depend on it may continue.
- **Cancellation:** anyone who may start the workflow may cancel it, with a reason.
  - Pending and ready steps become cancelled, and queued operations are cancelled.
  - Running operations finish; their evidence is kept and labelled as belonging to a cancelled run.

## 6. Audit

- **Audit events:** `workflow.started`, `workflow.step_started`, `workflow.step_blocked`, `workflow.step_finished`,
  `workflow.cancelled` and `workflow.finished`, each with the definition fingerprint.
- **Refusals** to start a step are audited with the CONTROL reason, like playbook preflight refusals.
- **Operations** created by a step carry `workflow_run_id` and `workflow_step` in `params`, which are covered by the
  audit export hash chain.

## 7. First workflows (v1), using only what's built

1. **Exposure review** (Profile A):
   1. Passive reconnaissance playbook.
   2. Wait for BLACK ICE ingest.
   3. `review`: a person triages the new findings of severity ≥ medium (validate, mark false positive, or leave).
   4. `checkpoint`: "Reassess after remediation?"
   5. `wait`: until a person marks the findings remediated.
   6. `operation`: re-run the collector that produced each finding (low risk needs approval as usual).
   7. `review`: contradiction flags and reopened findings.
2. **Remediation reassessment** (Profile A): steps 5–7 of the above on their own, started from a finding marked
   remediated.

Both are useful without SHIELD, and neither needs a new collector, permission or external service.

## 8. Threats and mitigations

| Threat | Mitigation |
|---|---|
| A workflow used to launder permissions ("the workflow did it") | No NEXUS role or service identity; every step runs as a named person through the normal route functions; checks at step start |
| A stale decision carried forward | Approvals never re-used; scope, role and proof re-evaluated per step; approval lifetimes unchanged |
| A model starting or steering work | Agents can't start, start steps or answer checkpoints; predicates are a fixed list, not model output |
| Runaway or looping work | Definitions are DAGs checked at import; retries capped at 2; per-step and per-run deadlines; existing per-target budgets still apply |
| Fake progress | Steps only complete from real events; unbuilt kinds are unavailable, never simulated |
| State tampering | Transition trigger; insert-only step events; audit export chain |

## 9. Tests required

- The definition validator: cycles, unknown dependencies, unavailable kinds and unknown predicates are refused at
  import.
- Every transition allowed or refused by the trigger, from each role.
- A step is refused at start when, since the run began, the role was lowered, the scope version changed, the target
  was excluded or the approval expired. The run is blocked with the reason, not failed silently.
- Approving the start of a run never approves an operation (direct test on the approvals table).
- Timeouts cancel queued operations; cancellation keeps evidence and labels it.
- Retries create new operations needing new approvals, and never follow a denial.
- Advancing is idempotent under concurrent calls (two sessions advancing the same run).
- The agent role and agent-originated requests can't start runs or steps.
- An end-to-end test of workflow 1 in fixture mode, with simulated evidence labelled as such.

## 10. Build order once approved

1. Migration, definition validator, state machine and advance function. No UI yet; tests only.
2. Workflow 1, with the run page (steps, states, links to operations, findings and evidence) under JANUS CORE →
   NEXUS.
3. Workflow 2 and a "Reassess" entry point on remediated findings.
4. The CHRONICLE feed from `workflow_step_events` (with the CHRONICLE build).
5. SHIELD step kinds only after SHIELD exists and its own design is approved.

Effort: about the size of BLACK OPS v1. One migration. No paid services and no new external dependencies.
